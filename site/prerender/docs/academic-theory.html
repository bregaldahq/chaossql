Theory

Formal Theory & Mathematical Foundation

Mathematical foundations of concurrency fuzzing: Bernstein conditions, Adya CSR theorems, Burckhardt PCT probability bounds, and Zeller delta-debugging.

1. Formal Model of Transactions and Execution Schedules

ChaosSQL establishes its mathematical foundations upon classical database concurrency theory developed by Bernstein, Goodman, Papadimitriou, and Adya.

Formal Definition of a Transaction

A transaction Ti is formally defined as an ordered tuple:

Ti = (Oi, <i)

Where:

  • Oi is a finite set of atomic read operations ri[x], write operations wi[x], commit ci, or abort ai, accessing data items x ∈ D.
  • <i is a strict partial order over Oi reflecting the deterministic program flow of the transaction.
  • There exists exactly one terminal operation ti ∈ {ai, ci}, which is the maximal element under <i.

Formal Definition of an Execution Schedule (History)

A concurrent execution schedule S over a finite set of transactions T = {T1, T2, …, Tn} is a partial order S = (bigcupi=1n Oi, <S) satisfying:

  1. bigcupi=1n <i  ⊆  <S (preserves the intra-transaction instruction ordering of each transaction).
  2. For any two conflicting operations oi, oj ∈ S (where i ≠ j), either oi <S oj or oj <S oi.

2. Bernstein Conflict Conditions & CSR Theorem

Bernstein Conflict Condition (1966)

Two operations oi, oj ∈ S belonging to distinct transactions (i ≠ j) are in direct conflict if and only if they access the same data entity x ∈ D and at least one of them is a write mutation (w):

Conflict(oi, oj) ⟺ (target(oi) = target(oj) = x)  ∧  (oi is w  ∨  oj is w)

Direct Serialization Graph (Adya Dependency Graph)

Given an execution schedule S, the Direct Serialization Graph SG(S) = (V, E) is a directed graph where:

  • Vertices V = T correspond to the set of committed transactions.
  • A directed edge (Ti → Tj) ∈ E exists if and only if there exist oi ∈ Ti and oj ∈ Tj such that oi <S oj and Conflict(oi, oj).

The Three Fundamental Dependency Relations (Atul Adya, 1999)

  1. Read Dependency (wr): Ti  —wr→  Tj if Ti writes a version of x and Tj subsequently reads that same version.
  2. Overwrite Dependency (ww): Ti  —ww→  Tj if Ti writes a version of x and Tj subsequently overwrites x.
  3. Anti-Dependency (rw): Ti  —rw→  Tj if Ti reads a version of x and Tj subsequently writes a newer version of x, invalidating the currency of Ti's read.

Fundamental Theorem of Conflict Serializability (CSR)

Fundamental Theorem: A concurrent history S is Conflict Serializable (S ∈ CSR) if and only if its Serialization Graph SG(S) is a Directed Acyclic Graph (DAG).

The existence of any directed cycle (T1 → T2 → … → T1) proves that the execution is semantically inconsistent and possesses no equivalent serial ordering.

3. Probabilistic Concurrency Testing (PCT-SQL) (Burckhardt & Musuvathi)

Naive random concurrency testing fails due to combinatorial explosion. For n transactions executing m steps each, the total number of possible interleavings Ω grows factorially:

|Ω| = ((n · m)!)⁄(m!)n

For merely 5 transactions with 3 steps each, there exist 168,168,000 possible interleavings. The probability of hitting a critical context switch purely by chance is below 10-6.

Burckhardt Lower Bound Theorem (ASPLOS 2010)

Burckhardt and Musuvathi proved that if a concurrency bug has a schedule depth d (the number of priority constraints or critical context switches required to trigger it), the Probabilistic Concurrency Testing (PCT) algorithm finds it in a single run with at least this probability:

ℙ(Detection) ≥ 1⁄(n · kd-1)

Where n is the number of concurrent threads and k is the total number of executed steps.

Scope: The bound below is a property of PCT. The ChaosSQL engine schedules with seeded jitter, and only the transparent proxy uses a PCT-style scheduler, so treat these numbers as the reference model for why a few hundred seeded runs are worth it, not as a measured detection rate.

Practical Application to Relational Databases

  • Seminal empirical research (Lu et al., ASPLOS) demonstrates that ~96% of real-world concurrency bugs have depth d = 1 or d = 2 (Lost Update requires d=1; Write Skew requires d=2).
  • For d = 2, the single-run detection probability is ℙ ≥ 1⁄(n · k). In a test with 4 workers and 25 steps (n=4, k=25), ℙ ≥ 1⁄100 = 1%.
  • In a short batch of R = 300 runs:

ℙ(Find Bug in R Runs) = 1 - (1 - 1⁄100)300 ≈ 1 - e-3 ≈ 95.02%

4. Minimization with Andreas Zeller Delta-Debugging (ddmin)

Formal Definition of 1-Minimality

Let C = ⟨ op1, op2, …, opN ⟩ be the ordered sequence of scheduled operations that triggers an invariant failure test(C) = FAIL.

A subsequence C* ⊆ C is defined as 1-Minimal if and only if:

test(C*) = FAIL   ∧   ∀ op ∈ C*: test(C* ∖ {op}) = PASS

The ddmin Implementation in ChaosSQL

ChaosSQL replays each candidate subsequence against a freshly reset database and keeps it only when it reproduces the same failure signature: a violation status on the same invariant. A candidate that ends in a different status, such as an execution error from FOREIGN KEY constraint failed caused by removing the operation that created a parent row, does not count as a reproduction and is discarded.

  1. Replays are memoized, so a subsequence already tested is never executed twice.
  2. After ddmin converges, a final audit removes each remaining operation once and confirms that the failure disappears, which establishes 1-minimality.
  3. The shrinker does not compute data dependencies between operations; it relies on the signature check to reject candidates that break referential integrity.

5. Linearizability and Black-Box Observations (Elle)

Inspired by the testing methodology of Kyle Kingsbury (Jepsen) and Peter Alvaro (VLDB 2020), ChaosSQL infers transactional anomalies strictly from client-observable operation histories (reads, writes, commits, and returns). No internal database engine instrumentation or custom storage bytecode is required, making ChaosSQL universally compatible with any SQL-compliant relational database.
