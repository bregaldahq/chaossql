A lost update in four steps

This is a real run of the banking example, recorded with seed 42. Nothing on this page is mocked.

  1. Two withdrawals read the same balance

    Both transactions read $1,000 before either one writes. Each is correct on its own.

  2. Each one writes its own result

    The first debits $19 and saves $981. The second debits $11 and saves $989.

  3. The second write erases the first

    The account ends at $989 instead of $970. A $19 debit vanished and no error reaches the logs.

  4. ChaosSQL proves it and hands you the test

    The invariant fails, the engine replays the exact order, and delta debugging keeps only the 2 transactions that cause it, in repro_test.go.

Words used here

Invariant
A rule your data must always obey, written as a SQL query. For example: the balance equals the opening balance minus every debit.
Isolation level
How much one transaction can see of another that is still running. Weaker levels are faster and allow more of these bugs.
Seed
A number that fixes the order of every operation, so the same seed replays the same run.

Run it on every pull request

The GitHub Action runs your scenarios, writes a JUnit report and a job summary, and attaches the reproduction.

A violation does not fail the job by itself: gate merges on the JUnit report, or on the is-regression output from ChaosSQL Cloud, which compares each pull request against main and comments the minimal trace.

.github/workflows/concurrency.yml
name: Concurrency Guard
on:
  pull_request:
    branches: [main]

permissions:
  contents: read
  pull-requests: write

jobs:
  concurrency:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: bregaldahq/chaossql@v1.6.0
        with:
          spec-path: chaos/transfers.yaml
          seed: '42'
          export-junit: chaossql-junit.xml
          export-repro: 'true'
          # Optional, ChaosSQL Cloud: baseline against main and PR comments
          cloud-token: ${{ secrets.CHAOSSQL_CLOUD_TOKEN }}

Questions engineers ask first

Does it run against my production database?

No, and it must not. Every run resets the schema and seed data, so point it at a disposable database: a CI service container or a local copy.

Which databases does it support?

PostgreSQL, MySQL and SQLite, plus an in-memory driver for the browser playground. SQLite serializes writes at its default level, so most anomalies show up on PostgreSQL, MySQL or weaker isolation levels.

How is this different from a load test?

A load test measures throughput and hopes a race happens. ChaosSQL chooses the interleaving from a seed, checks a business rule after every run and replays the exact order that broke it.

Is it really deterministic?

The same spec and seed always produce the same schedule. Databases still decide some timing on their own, and ChaosSQL reports that difference instead of hiding it.

Will a violation fail my build?

Not by itself: the command exits successfully and records the violation in the JUnit report and job summary. Gate on those, or on the is-regression output from ChaosSQL Cloud.

What do I need to install?

Only the binary: go install gives you a single static Go program with no CGO. The Python and TypeScript SDKs call the same binary.

What does the audit include?

A 45 minute kickoff, the five most critical transactions mapped, more than 100,000 schedules explored, Go reproduction tests, a final report presented to your team and three months of Cloud Team.
